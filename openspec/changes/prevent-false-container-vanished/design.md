# Design

## Context

Node 的对账线程先枚举 Docker，再逐个采集运行指标；`_apply_container` 期间可耗费数十秒。当前代码在这之后读取缓存名称作为 `known`，与先前枚举所得的 `live` 做差，导致枚举后新建的容器被误判消失。`set_port_info` 可在尚无缓存条目时创建条目。删除候选由 WSS 在快照前发给 Ctrl；Ctrl 按机器和名称直接软删除数据库记录。事件采集还读取 `status` 而生产 Docker 事件主要给出 `Action`。

## Goals / Non-Goals

**Goals:**

- 让单轮对账只评价该轮开始时已知的容器代际；新建、重建及状态采集交错不触发误删。
- 对消失候选做 Docker 单容器再确认；不可判定时保留事实并报告采集错误。
- 在发送前识别过期删除候选，并修复 `Action` 事件兼容。

**Non-Goals:**

- 本变更不修复已经软删除的 `jyz`、`test2` 生产数据，也不修改 `daity` 挂载。
- 不在这次 Node 仓库变更中修改 Ctrl 数据库结构或现有 WSS 线路字段；跨进程同名代际的端到端身份协议另见 Global `QUESTIONS.md`。

## Decisions

### 1. 观察快照与代际令牌

每轮 Docker 枚举前，在缓存锁内截取“当前确有 Docker 对象证据”的名称及其本地代际令牌。创建受理、构建开始、同名重建和显式忘记旧代时更新令牌；普通指标更新不改变代际。本地代际只在当前 Node 进程/缓存内有效，不是 Docker 对象身份，也不是 Q70 的跨进程操作代际，不能被发送给 Ctrl 作为严格代际证明。枚举完成后只比较该起始快照与 Docker 列表。候选进入删除队列前，再在锁内确认代际未变、没有正在创建的 pending/build，防止慢速枚举抹掉新代。

创建 API 在返回受理成功前同步登记初始 `building`/`creating`；后台线程沿用该过渡态并负责后续推进，受理失败时按现有失败语义收尾。过渡态本身不进入 Docker 消失候选，且其存续期间否决旧代候选。这同时封住 Ctrl 可能在后台线程启动前收到缺席快照的窗口。

仅在枚举后读取 `set(_cache)` 的现有做法会混合两个时刻。单靠延长冷却时间会延后错误，却不能证明不存在，因此不采用。

### 2. 两级存在性确认

对每个差集候选，在不持有缓存锁时做一次 Docker 单容器查找。明确 NotFound 才有资格进入删除队列；找到对象则保留缓存并等待下一轮收敛；查询异常则保留缓存并置 `collect_error`。再确认返回后，在缓存锁内复核代际与创建状态，才移除旧条目并排队。这样避免 Docker API 调用堵塞其他缓存更新。

### 3. 删除队列携带本地代际

队列内部保存名称和代际，而不是只有名称。创建开始即撤销该名称旧代候选；WSS 取出后发送前再次检查候选代际和 Docker 存在性。已失效的候选不发送。单容器查询失败时不把“不知道”解释为删除，保留候选供下轮对账或重试。线路上暂保持 `type=delete` 与 `container_name` 不变。

这层检查缩小 Node 到 Ctrl 的发送窗口，但仅凭名称无法给跨进程消费者提供严格代际比较；这一剩余边界列入 Q70。Ctrl 的独立快照缺席软删路径由配套变更 `guard-container-vanish-deletion` 处理。

### 4. 事件动作归一化

Docker 事件动作优先读取 `Action`，缺失时回退历史 `status`；状态事件更新缓存与轨迹，噪声事件忽略，未知事件告警。保持原有 ready-check 守卫，事件本身不构成消失证据。

## Risks / Trade-offs

- [每轮候选多一次 Docker 查询] → 只查询差集候选，不对所有容器增加请求；查询失败保留缓存并在下轮重试。
- [缓存锁与外部 Docker 查询交错] → Docker 调用不持锁；调用前后用代际令牌与 pending 状态双重验证。
- [delete 帧已发出后才发生同名重建] → Node 无法撤回在途帧；本变更不宣称跨进程绝对安全，Q70 决定是否让 Ctrl 保存并比较 Docker 对象身份。
- [事件格式因 Docker 版本而异] → 同时覆盖 `Action` 与 `status`，并用真实格式样本及兼容测试验收。
- [先部署 Node 会留下 Ctrl 快照缺席路径] → 部署顺序固定为先 Ctrl `guard-container-vanish-deletion`、后 Node；Node 上线前 Ctrl 已把名称消失线索降级为待核实，不能把 Node 单侧修复当成完整防护。

## Migration Plan

先部署 Ctrl `guard-container-vanish-deletion` 防护，再部署 Node 修复：Ctrl 的防护先阻止显式 `delete` 帧和快照缺席两条路径直接软删，Node 上线前即使旧 Node 仍发送名称线索，Ctrl 也只标待核实。Node 部署后观察对账日志中消失候选的再确认结果和 `delete` 帧；无需数据库迁移或 WSS 协议升级。部署前保留现有代码版本；若 Node 对账出现异常，回滚 Node 代码并重启 Node 服务，但不要单独回滚 Ctrl 防护。回滚不会自动恢复此前已软删除的 Ctrl 记录，生产数据修复另行核对。
